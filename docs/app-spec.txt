<project_specification>
  <project_name>PolyScript - Multi-Language Transcription Service</project_name>

  <overview>
    Build a job-based, multi-language speech-to-text (STT) transcription service in a monorepo.
    
    The system consists of:
    - apps/marketing: Astro static marketing site (5 languages: en, de, es, fr, jp)
    - apps/web: Vite web app (React + TypeScript) for authenticated users
    - apps/admin: Vite admin panel for super admin system management
    - apps/api: FastAPI backend (HTTP API, SSE endpoints)
    
    Users sign up and become team admins. They can invite team members with different roles (ADMIN, MEMBER, VIEWER).
    The system supports full internationalization in 5 languages with localized UI and API responses.
    
    Jobs are processed asynchronously: upload → enqueue to Redis → worker service processes → results saved to DB.
  </overview>

    <!-- WORKER SERVICE -->
    <worker_service>
      - Worker runs as separate `apps/worker` service with dedicated event loop thread
      - Worker lifecycle:
        - Starts via `python apps/worker/main.py` or configured process manager
        - Initializes STT engines, storage backend, and Redis client on startup
        - Spawns consumer thread with its own asyncio event loop
        - Listens to SIGTERM/SIGINT for graceful shutdown
      - Consumer thread implementation:
        - Dedicated thread ("TranscriptionConsumer") runs consumer loop
        - Thread creates its own asyncio event loop via `asyncio.new_event_loop()`
        - Consumer blocks on Redis queue with 1s timeout to check shutdown flag
        - Processes jobs sequentially (no parallelization)
        - Graceful shutdown: completes current job, stops blocking queue, exits
      - Job processing pipeline (7 stages):
        1. Starting (0%): Mark job RUNNING, increment attempts, set started_at
        2. Downloading (0-10%): For URL jobs, download audio; uploads already stored
        3. Decoding (10-20%): Validate audio format, extract duration
        4. Transcribing (20-90%): Call STT engine (whisper-local, etc.)
        5. Formatting (90-95%): Normalize output, generate segments JSON
        6. Translating (95-98%): If target_language specified, translate (optional)
        7. Saving (95-100%): Save transcript to DB, mark SUCCEEDED
      - Download validation:
        - Enforces Content-Length when present and validates downloaded size
        - Logs SHA-256 checksum for auditability
        - Retries with exponential backoff on partial/failed downloads
      - Audio validation:
        - Detects codec/extension mismatches and corrupt files with explicit errors
        - Rejects zero-duration or empty audio
        - Supported formats: MP3, WAV, M4A, AAC, FLAC, AMR, AMR-WB, OGG, WEBM, MP4
      - GPU fallback:
        - On CUDA/MPS errors, fall back to CPU inference for Whisper/TranslateGemma
      - VAD telemetry:
        - Logs speech vs total duration ratio and warns when >90% is filtered
      - Monitoring:
        - Log validation failures, download errors, and accelerator fallbacks with job_id/team_id
      - Progress updates:
        - Update DB (progress_pct, progress_stage) on each stage transition
        - Publish to Redis pub/sub channel `job:{job_id}:progress`
        - SSE endpoint in apps/api listens to this channel for live updates
      - Retry policy:
        - On failure: increment attempts in DB
        - If attempts < max_retries: calculate backoff delay (backoff ** attempts), re-enqueue, mark QUEUED
        - If attempts >= max_retries: mark FAILED with error_code, error_message, finished_at
        - Configurable via QUEUE_MAX_RETRIES (default: 3) and QUEUE_RETRY_BACKOFF (default: 2)
      - Queue contract:
        - Queue key: `transcription:queue`
        - Work item payload (JSON):
          - job_id (uuid)
          - audio_ref (db reference to where audio is stored)
          - requested_language (nullable)
          - engine (nullable; resolved via default if null)
          - options (object)
      - Cancel handling:
        - Check Redis key `cancel:{job_id}` before processing
        - If set, mark job CANCELED immediately (best-effort)
    </worker_service>

    <!-- DELETION POLICY -->
    <deletion_policy>
      - Soft delete pattern: set deleted_at timestamp instead of hard delete
      - Grace period: configurable days before hard deletion (default 30)
      
      User Deletion:
        - User requests deletion → soft delete (set deleted_at)
        - If user is only ADMIN of a team → entire team loses access
        - Jobs created by user → orphaned (created_by remains but user marked deleted)
        - Transcript edits by user → kept for orphaned_content_retention_days, then deleted
        - OAuth accounts → deleted immediately
        - Refresh tokens → revoked immediately
        
      Team Deletion:
        - Team admin requests deletion → soft delete team
        - All team members lose access immediately
        - Jobs and transcripts → marked for deletion
        - Audio files → scheduled for cleanup after grace period
        - Stripe subscription → canceled immediately
        - Invoices → retained for legal/accounting (marked as archived)
        
      Content Deletion Criteria (extensible):
        - deleted_at older than DELETION_GRACE_PERIOD_DAYS → hard delete
        - Orphaned content older than ORPHANED_CONTENT_RETENTION_DAYS → hard delete
        - Expired invitations → delete immediately
        - Expired password reset tokens → delete immediately
        - Revoked refresh tokens older than 7 days → delete
    </deletion_policy>

      - cleanup_audio_files
